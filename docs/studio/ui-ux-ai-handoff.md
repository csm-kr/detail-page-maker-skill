## 0. Claude Design에 전달할 핵심 지시

Detail Page Studio는 AI 이미지 생성기가 아니라, 실제 상품 근거를 잠그고 여러 AI 제작 작업을 안전하게 병렬 실행한 뒤 결과를 검수·승인하여 상업 상세페이지로 조립하는 로컬 크리에이티브 운영 도구다.

다음 화면을 하나의 일관된 데스크톱 제품으로 설계한다.

1. 실제품 사진과 제품 사실 SSOT를 등록·잠그는 에셋 검수 화면
2. 필요한 광고 에셋을 AI Node 묶음으로 선택하고 일괄 실행하는 배치 빌더
3. 실행 중인 배치와 개별 AI Node의 상태·오류·재시도를 관리하는 작업 센터
4. 생성 결과를 원본과 비교하고 QA 근거를 확인해 승인하는 검수 화면
5. GIF·HyperFrames 편집, 상세페이지 조립, HTML 편집, 최종 QA와 내보내기 화면

디자인의 중심은 “AI가 무엇을 만들 수 있는가”가 아니라 다음 질문에 답하는 것이다.

- 지금 어느 단계인가?
- AI가 어떤 실제품 근거와 지시를 사용하고 있는가?
- 배치 전체와 개별 작업은 어디까지 진행됐는가?
- 실패한 작업만 안전하게 다시 실행할 수 있는가?
- 생성 완료, QA 통과, 사용자 승인, 게시 가능은 어떻게 다른가?
- 현재 버튼을 누르면 무엇이 바뀌고 무엇은 잠긴 채 유지되는가?

1440×900을 기본 프레임으로 설계한다. 1220px 이하에서는 Inspector와 작업 센터를 오버레이 패널로 바꾼다. 제작 기능의 모바일 최적화는 범위 밖이며, 좁은 화면에서는 상태 확인과 승인 근거 열람을 우선한다.

## 1. 제품 정의

### 1.1 한 문장 정의

실제 상품 근거를 SSOT로 고정하고 AI 이미지·모션 제작을 배치로 실행한 뒤, 근거 기반 QA와 사용자 승인만 통과한 에셋을 수정 가능한 HTML 상세페이지로 조립하는 로컬 Studio다.

### 1.2 사용자에게 약속하는 것

- AI는 실제품 SSOT 밖의 제품 형태·비율·재질·라벨·부품 위치를 임의로 바꾸지 않는다.
- 생성 결과는 원본을 덮어쓰지 않고 새 버전으로 남는다.
- 한 AI Node가 실패해도 같은 배치의 다른 Node와 기존 승인본은 유지된다.
- AI의 생성 완료는 사용자의 승인 완료를 뜻하지 않는다.
- 제품 동일성 하드 실패가 남아 있으면 조립과 게시를 할 수 없다.
- 조립된 개정판은 파괴적으로 다시 열지 않고 새 개정판에서 변경한다.

### 1.3 범위 밖

- 자유 배치형 범용 AI Node 그래프 편집기
- AI의 자동 승인·자동 조립·자동 게시
- 생성된 평면 이미지의 완전한 레이어 분해
- 클라우드 협업, 역할별 계정, 결제와 사용량 관리
- 조립된 개정판의 승인 이력을 지우는 직접 수정

## 2. 현재 상태와 이번 업데이트의 경계

### 2.1 현재 구현되어 있는 사실

- 상단바, 5단계 Stage Rail, 중앙 Workspace, 우측 Inspector 구조가 있다.
- 단계는 `에셋 검수 → GIF 편집 → 상세페이지 조립 → HTML 편집 → 최종 QA`다.
- 실제품 사진을 여러 장 등록하고 현재 개정판의 제품 사실 SSOT로 잠글 수 있다.
- 권장 에셋 최대 12개를 한 번에 작업으로 만들 수 있다.
- `god-tibo-gpt-image2-skill` 8장 자동 실행 또는 `queue` 대기열 등록을 선택할 수 있다.
- 자동 실행의 동시 작업 수는 1~4, 기본값은 4다.
- 각 작업은 `queued`, `running`, `completed`, `failed`, `cancelled` 상태를 가진다.
- 작업 완료 결과는 독립된 에셋 버전으로 등록되며 QA와 사용자 승인을 별도로 거친다.
- HTTP 변경과 SSE 이벤트를 통해 프로젝트 상태를 새로 고친다.
- 현재 작업 센터는 작업을 시간순으로 나열하는 단순 목록이다.

### 2.2 이번 UI/UX 업데이트에서 추가할 것

- `batchId` 기준 배치 그룹과 배치 전체 상태
- 사용자가 이해할 수 있는 `AI Node` 단위 진행 표시
- 배치 준비 상태를 검사하는 Preflight
- 배치별 완료·실패·검수 대기 요약
- 개별 실패 재시도와 실패한 Node 전체 재시도
- AI Node 상세에서 입력 근거, 프롬프트, 실행 이력, 결과와 오류 확인
- 원시 작업 종류 대신 사용자용 이름과 단계 표시
- 생성 완료와 QA·승인 완료를 분리한 상태 표현
- 실행기 선택과 동시성은 기본 UI에서 감추고 `고급 설정`으로 이동
- 작업 센터를 닫아도 상단바와 에셋 보드에서 진행 상황 유지

### 2.3 구현 사실과 목표 설계 표기

이 문서에서 `현재`는 기존 인터페이스로 바로 표현할 수 있는 내용, `목표`는 서버 계약 또는 UI 구조 업데이트가 필요한 내용이다. Claude Design은 목표 화면을 설계하되 현재 상태에서도 단계적으로 구현할 수 있게 구성한다.

## 3. 핵심 용어와 사용자 멘탈 모델

| 용어 | 사용자에게 보이는 의미 | 설계 규칙 |
| --- | --- | --- |
| 프로젝트 | 한 상품의 근거·에셋·HTML·QA 전체 묶음 | 상품명과 현재 개정판을 항상 상단에 표시 |
| 제품 사실 SSOT | 실제 SKU의 형태와 라벨을 판정하는 원본 사진·사실 | 광고 에셋과 시각적으로 분리 |
| SSOT 잠금 | 현재 개정판이 사용할 실제품 근거 확정 | 생성 전에 반드시 통과하는 하드 게이트 |
| 에셋 | 상세페이지에 사용할 이미지·GIF·그래픽 역할 | 역할 단위로 한 개의 현재 채택 버전을 가짐 |
| 에셋 버전 | 같은 에셋의 원본·생성·수정 후보 이력 | 덮어쓰기 없이 버전 칩으로 전환 |
| 배치 | 같은 SSOT와 실행 설정으로 시작한 AI Node 묶음 | 하나의 진행 요약과 여러 독립 결과를 가짐 |
| AI Node | 한 개의 에셋 결과를 만드는 독립 작업 | Node.js가 아니며 자유 배치형 그래프도 아님 |
| 실행 시도 | 한 AI Node를 실제로 실행한 한 번의 기록 | 재시도 시 이전 오류와 결과를 보존 |
| QA | 제품 동일성·시각 품질·파일 무결성 검사 | AI의 판단 근거를 보여주되 승인과 분리 |
| 조건부 채택 | 사용자가 QA 판단과 다르게 현재 후보로 선택 | 하드 실패를 지우거나 조립을 허용하지 않음 |
| 승인 | QA 통과 후 사용자가 사용을 확정 | 녹색 완료 상태는 이 시점부터 사용 |
| 조립 잠금 | 승인 버전과 SHA-256을 현재 개정판에 고정 | 이후 에셋·GIF는 읽기 전용 |
| 새 개정판 | 잠긴 조립본을 보존한 다음 변경 작업 공간 | 영향받는 에셋만 다시 검수 |

AI Node는 사용자에게 “한 장을 만드는 하나의 독립 작업”으로 설명한다. 내부 작업 종류인 `imagegen.generate.product-ssot` 같은 문자열은 기본 UI에 노출하지 않는다.

## 4. UX 목표와 성공 기준

### 4.1 UX 목표

1. 사용자는 3초 안에 현재 단계, 활성 배치 수, 주의가 필요한 작업 수를 파악한다.
2. 배치 시작 전에 참조 SSOT, 제작 대상, 제외 대상과 실행 개수를 확인한다.
3. 배치 실행 중 다른 단계로 이동해도 진행 상황을 잃지 않는다.
4. 일부 실패 시 성공 결과를 보존한 채 실패한 Node만 다시 실행한다.
5. 생성 완료·QA 대기·검수 필요·승인의 차이를 색상 없이도 이해한다.
6. 하드 게이트가 잠긴 이유와 다음 해결 행동을 같은 위치에서 확인한다.
7. 모든 AI 결과는 사용한 SSOT, 프롬프트, 실행기, 파일 해시와 연결된다.

### 4.2 금지할 UX

- 정확한 근거 없이 가짜 퍼센트 진행률을 표시하지 않는다.
- 배치 일부 실패를 전체 실패처럼 처리하지 않는다.
- 생성 완료 카드를 녹색 `완료`만으로 표시해 승인된 것으로 오해시키지 않는다.
- 내부 실행기 이름이나 오류 스택을 사용자용 제목으로 노출하지 않는다.
- 위험한 작업을 단순 토스트 한 번으로 확정하지 않는다.
- 비활성 버튼만 두고 이유를 설명하지 않는 상태를 만들지 않는다.
- AI가 사용자 확인 체크박스를 대신 선택하거나 승인 버튼을 호출하지 않는다.

## 5. 사용자와 역할

### 5.1 주 사용자: 상세페이지 제작 운영자

실제품과 공급처 근거를 확보하고 AI 에셋 제작, 비교, 수정, 승인, 조립과 내보내기를 한 흐름에서 수행한다. 디자인 툴 숙련도보다 상품 정확성과 작업 재현성이 중요하다.

주요 요구:

- 한 번에 여러 결과를 만들되 결과는 개별 판단
- 잘못된 한 장만 빠르게 수정·재실행
- 실제품과 AI 결과를 크게 비교
- 지금 게시 가능한지 명확한 판단

### 5.2 검수자

운영자와 같은 사람일 수 있다. QA 점수보다 실제품 근거와 하드 실패 내용을 먼저 보고 승인 여부를 결정한다.

### 5.3 AI와 시스템의 역할

| 역할 | 할 수 있음 | 할 수 없음 |
| --- | --- | --- |
| Studio | 상태 검증, 저장, 잠금, 비교, 이력, 게이트 계산 | 제품 사실을 임의로 추정 |
| 생성 AI | 확인된 입력과 프롬프트로 후보 생성·수정 | 결과 자가 승인 |
| Codex QA | 원본·후보 비교, 하드 실패와 경고 기록 | 사용자 승인, 조건부 채택, 조립, 게시 |
| 사용자 | SSOT 확인, 프롬프트 확정, 승인·보류·재시도 | 하드 실패를 삭제하거나 이력을 소급 변경 |

| 단계 | 사용자 목표 | 주요 행동 | 시스템·AI 행동 | 불안·실패 지점 | UX 대응 | 완료 신호 |

| 4. 배치 계획 | 필요한 에셋 한 번에 선택 | 역할 선택, 고급 설정 검토 | 중복·진행 중 역할 제외, Preflight | 무엇이 제외됐는지 모름 | `제작 대상/제작 중/완성됨/차단`을 행마다 표시 | 실행 가능 Node 수 확정 |
| 5. AI 배치 실행 | 다른 일을 하면서 진행 확인 | 배치 시작, 작업 센터 닫기 | Node별 병렬 실행·결과 등록 | 일부 실패, 연결 중단 | 상단 집계, 배치 그룹, 개별 실패 격리 | 제작 성공·실패 집계 |
| 6. QA와 검수 | 사용할 버전 결정 | 원본 비교, 수정·보류·승인 | 자동 검사, Codex 시각 QA | 생성 완료를 승인으로 오해 | `QA 대기 → 검수 필요 → 승인` 분리 | 필수 에셋 승인 |
| 7. 모션 편집 | GIF 증거 장면 완성 | 레이어 수정, 재렌더 | HyperFrames 후보와 프레임 QA | 중간 프레임의 제품 붕괴 | 동일 시점 비교와 레이어 잠금 | GIF 승인 |
| 8. 조립 잠금 | 사용할 파일 확정 | 버전·해시 확인, 조립 확정 | 미처리 작업·하드 실패 검사 | 승인 누락 | 차단 이유와 해당 에셋 바로가기 | 조립 Manifest |
| 9. HTML 편집 | 카피와 레이아웃 완성 | 직접 편집, undo, 체크포인트 | 자동 저장, viewport override | 에셋까지 바뀔까 걱정 | 에셋 읽기 전용 안내 | HTML 편집 완료 |
| 10. 최종 QA·게시 | 안전한 결과 내보내기 | QA 요청, 최종 승인, 내보내기 | 97점·하드 실패·재현 검사 | 초안과 게시본 혼동 | 내보내기 종류와 게이트 분리 | 게시용 단일 HTML |

### 6.1 Happy Path

```text
프로젝트 열기
  → 실제품 사진 등록
  → 제품 사실 SSOT 잠금
  → 전체 에셋 일괄 제작
  → Preflight 통과
  → AI Node 병렬 실행
  → 작업 센터에서 배치 진행 확인
  → 결과별 QA
  → 원본·후보 비교
  → 사용자 개별 승인
  → GIF 편집·승인
  → 조립 잠금
  → HTML 편집
  → 최종 QA
  → 사용자 최종 승인
  → 게시용 HTML
```

### 6.2 Partial Failure Flow

```text
7개 Node 실행
  → 5개 제작 성공
  → 1개 실행 실패
  → 1개 QA 하드 실패
  → 성공 5개는 그대로 에셋 보드에 유지
  → 실행 실패 Node만 같은 입력으로 재시도
  → QA 실패 Node는 원본 비교 후 프롬프트 수정 버전 생성
  → 두 Node만 다시 QA
  → 전체 필수 에셋 승인 뒤 조립
```

### 6.3 조립 뒤 변경 Flow

```text
잠긴 V1에서 에셋 변경 요청
  → 직접 수정 차단
  → 새 개정판 V2 만들기
  → 변경 에셋 선택
  → Dependency Graph가 관련 GIF·HTML 섹션 계산
  → 영향 항목만 재제작·재승인
  → V1 보존, V2 새 조립 잠금
```

### 7.4 Inspector

Inspector는 현재 선택된 대상 하나에만 반응한다.

- 에셋 선택: 버전, QA, 승인, 프롬프트 수정
- AI Node 선택: 입력, 진행 단계, 실행 이력, 오류, 재시도
- GIF 레이어 선택: 속성, 잠금 필드, 재렌더
- HTML 레이어 선택: 텍스트와 스타일, viewport 범위

Inspector가 비어 있을 때는 “선택 없음”만 보여주지 말고 현재 화면에서 선택할 수 있는 대상과 다음 행동을 한 문장으로 안내한다.

### 7.5 작업 센터

현재의 단순 Modal 목록을 목표 설계에서는 지속형 우측 Drawer로 확장한다.

- 데스크톱: 폭 560px, 상단바 아래부터 전체 높이
- 1220px 이하: 전체 화면 Overlay
- 닫아도 실행은 계속됨
- 다시 열면 이전 필터와 선택한 배치를 복원
- 배치 상세에서 `에셋 보드에서 보기`로 이동 가능

## 8. 화면별 UI/UX 설명

### 8.1 에셋 검수

목표:

실제품 근거, AI 배치 제작, 결과 검수와 승인을 하나의 단계에서 수행한다.

화면 순서:

1. Header: 단계 설명과 등록·생성 행동
2. 제품 사실 SSOT Panel
3. 활성 배치 Activity Strip
4. 전체 결과 Board
5. 에셋 Library + Compare Workspace
6. Inspector

제품 사실 SSOT Panel:

- 잠금 전에는 사진 추가, 사진별 근거 상태, `SSOT 잠금`을 보여준다.
- 잠금 뒤에는 `REV-001에 잠김`, 사진 수, 라벨, 색상, 잠금 시각을 요약한다.
- 잠금 뒤 기본 Primary Action은 `전체 에셋 일괄 제작`이다.
- `SSOT로 에셋 제작`은 한 개를 만드는 Secondary Action으로 둔다.
- 잠금을 해제하는 행동은 제공하지 않는다. 변경은 새 개정판으로 연결한다.

활성 배치 Activity Strip:

- 실행 중인 배치가 있을 때만 SSOT Panel과 결과 Board 사이에 나타난다.
- 예: `화이트 에셋 7개 · 제작 4 · 대기 2 · 실패 1`
- `작업 센터 열기`와 `실패 1개 보기`를 제공한다.
- Workspace를 과도하게 밀어내지 않도록 한 줄 높이로 유지한다.

전체 결과 Board:

- 역할별 카드 Grid
- 상태, 썸네일, 에셋명, 버전, QA 상태, 현재 행동
- 제작 중 카드는 실제 카드 자리를 Skeleton으로 예약
- 실패 카드는 썸네일 대신 오류 요약과 `다시 실행`
- 완료 카드는 `원본 보기`, `수정`, `검수·비교`
- 승인 카드는 `사용 중인 버전` 배지

Compare Workspace:

- 나란히, 겹치기, 차이 강조
- 양쪽 확대·이동 동기화
- GIF는 같은 시점 재생·스크러빙
- 버전 칩은 원본, V1, V2와 상태를 함께 표시
- QA 증거를 클릭하면 해당 이미지 영역 또는 GIF 시점으로 이동

종료 조건:

- 필수 에셋마다 승인 버전이 있음
- 제품 동일성 하드 실패 0건
- 관련 생성·QA 작업이 모두 Terminal 상태

### 8.2 GIF·HyperFrames 편집

목표:

완성 GIF 픽셀을 직접 고치지 않고 HyperFrames 원본의 선택 레이어를 수정해 새 후보를 만든다.

레이아웃:

- 왼쪽: Layer List
- 가운데: Motion Canvas와 Timeline
- 오른쪽: 선택 레이어 Inspector

행동 위계:

- Primary: `변경 후보 렌더 요청`
- Secondary: `프롬프트로 수정`
- Tertiary: 재생, 화면 맞춤, 레이어 숨김

제품 레이어는 잠금 아이콘과 SSOT 참조를 보여준다. 제품 형태를 바꾸는 속성은 직접 편집할 수 없고 배경·텍스트·효과 등 허용 필드만 노출한다.

### 8.3 상세페이지 조립

목표:

실제로 사용할 승인 버전과 해시를 확인하고 현재 개정판을 잠근다.

왼쪽 Gate List:

- 필수 에셋
- 선택 버전
- QA 통과
- 사용자 승인
- 해시 검증
- 미처리 작업

오른쪽:

- 실제 조립 Preview
- 에셋을 클릭하면 사용 위치 강조

Primary Action:

- 가능: `승인 버전으로 조립 확정`
- 불가: 비활성 버튼 옆에 차단 이유 수와 `문제 항목 보기`

조립 확인 Dialog에는 고정할 에셋 수, 현재 개정판, 이후 읽기 전용이 된다는 점을 다시 표시한다.

### 8.4 HTML 편집

목표:

승인 에셋을 유지한 채 카피, 레이아웃과 반응형 표현을 다듬는다.

- 800, 390, 320px Viewport
- 레이어 직접 선택
- Inspector 속성 편집
- 자동 저장
- Undo/Redo
- 이름 있는 Checkpoint
- `이 화면에만 수정` 범위 표시

에셋 교체나 AI 재생성 행동은 이 화면에 넣지 않는다. 요청 시 `새 개정판 만들기`로 안내한다.

### 8.5 최종 QA·내보내기

목표:

게시 가능한 상태와 아직 해결해야 할 상태를 명확히 구분한다.

- 상용 점수
- 제품 동일성 하드 실패
- 반응형
- 에셋 무결성
- GIF 재생
- 카피 근거
- HTML 인터랙션
- 사용자 최종 승인

내보내기 행동:

- `검토용 초안`: QA 전에도 가능, 명확한 Draft 표시
- `Studio 프로젝트 묶음`: 재현과 보관
- `최종 사용자 승인`: 게시 조건을 다시 확인
- `게시용 단일 HTML`: 97점 이상, 하드 실패 0건, 최종 승인 뒤에만 가능

## 9. AI Node 배치 처리 UX

### 9.1 핵심 개념

배치는 실행 단위의 묶음이고 AI Node는 결과 단위다.

```text
Batch: 화이트 제품 에셋 7종
  ├─ Node 1: 히어로 제품 이미지
  ├─ Node 2: 한 쌍 플랫레이
  ├─ Node 3: 착용 장면
  ├─ Node 4: 구조 증거
  ├─ Node 5: 소재 매크로
  ├─ Node 6: 운전 장면
  └─ Node 7: 여름 야외 장면
```

각 Node는 같은 SSOT 잠금을 공유하지만 프롬프트, 역할, 결과, QA, 오류와 재시도 이력은 독립적이다.

### 9.2 배치 진입 조건

`전체 에셋 일괄 제작` 버튼은 다음 조건에서 활성화한다.

- 현재 개정판이 조립 전 단계
- 실제품 SSOT가 현재 개정판에 잠겨 있음
- 잠긴 원본 해시가 유효함
- 새로 만들 수 있는 역할이 한 개 이상 있음

비활성일 때 버튼 Tooltip에 그치지 않고 바로 아래에 다음 행동을 표시한다.

- `실제품 사진을 먼저 등록하세요`
- `라벨과 색상을 확인해 SSOT를 잠그세요`
- `현재 개정판에는 새 제작 대상이 없습니다`
- `조립된 개정판입니다. 새 개정판에서 제작하세요`

### 9.3 Batch Builder

배치 빌더는 넓은 Dialog 또는 별도 Workspace Overlay로 설계한다. 한 화면에서 전체 맥락을 확인할 수 있게 하고 불필요한 다단계 Wizard는 피한다.

구조:

```text
┌───────────────────────────────────────────────────────────────┐
│ 전체 에셋 일괄 제작                         닫기               │
│ REV-001 · SSOT 잠김 · 실제품 사진 8장                          │
├──────────────────────────────────────┬────────────────────────┤
│ 제작 대상                            │ 배치 요약               │
│ [✓] 히어로 제품 이미지  제작 대상    │ 7개 제작                │
│ [✓] 한 쌍 플랫레이      제작 대상    │ 0개 제외                │
│ [ ] 착용 장면           제작 중      │ 실행 준비 통과          │
│ [ ] 구조 증거           완성됨       │                        │
│ ...                                  │ 고급 설정 ▾             │
│                                      │ 실행기: 자동             │
│                                      │ 동시 작업: 4             │
├──────────────────────────────────────┴────────────────────────┤
│ [✓] 실제품 SSOT를 모든 Node의 동일성 기준으로 사용            │
│ 취소                              선택한 7개 제작 시작          │
└───────────────────────────────────────────────────────────────┘
```

제작 대상 행:

- Checkbox
- 사용자용 에셋명
- 한 줄 목적 설명
- 역할 ID는 보조 정보로만 표시
- `제작 대상`, `제작 중`, `완성됨`, `차단` 상태
- 행 확장 시 Prompt Preview와 출력 설정

기본 선택 규칙:

- 새 역할만 선택
- 이미 완성된 역할과 활성 작업이 있는 역할은 선택 불가
- 제외 이유를 행 안에 표시
- 사용자가 이전 선택을 바꾸면 우측 요약을 즉시 갱신

고급 설정:

- 실행 방식: `자동 병렬 실행`, `대기열만 등록`
- 동시 작업 수: 1~4
- 출력 크기
- 실행기 세부 이름은 도움말 안에서만 표시

기본 UI에서는 `god-tibo-gpt-image2-skill`보다 `8장 자동 병렬 실행`을 먼저 보여준다. 내부 구현명은 장애 진단이나 실행 이력에서 확인할 수 있다.

### 9.4 Preflight

실행 버튼을 누르기 전에 다음 항목을 검사하고 같은 Dialog 안에서 결과를 보여준다.

| 검사 | 통과 | 경고 | 차단 |
| --- | --- | --- | --- |
| SSOT 잠금 | 현재 개정판에 잠김 | - | 미잠금·개정판 불일치 |
| 원본 무결성 | 해시 일치 | 일부 저해상도 | 파일 누락·해시 불일치 |
| 제작 대상 | 새 역할 | 기존 결과 교체 가능성 | 0개·중복 역할 |
| 프롬프트 | 필수 지시 존재 | 너무 긴 지시 | 비어 있음 |
| 실행기 | 준비됨 | 비공개 실행 방식 의존 | 로그인·실행기 사용 불가 |
| 동시성 | 1~4 | 시스템 부하 안내 | 범위 밖 |

Preflight는 `통과 5 · 경고 1 · 차단 0`처럼 요약한다. 경고는 확인 후 진행할 수 있고 차단은 해결 행동을 제공한다.

### 9.5 실행 시작

Primary Action 문구는 선택 수를 포함한다.

- `선택한 7개 제작 시작`
- Queue 모드: `선택한 7개 대기열 등록`

제출 중:

- Dialog를 즉시 닫지 않는다.
- 버튼에 `7개 작업 등록 중`을 표시한다.
- 서버가 원자적으로 모든 Node를 만들면 성공 상태로 전환한다.
- 성공 후 Dialog를 닫고 작업 센터에서 새 배치를 선택한 상태로 연다.

실패 시:

- 하나도 생성되지 않은 원자 실패인지, 일부 Node가 만들어졌는지 구분한다.
- 현재 서버 계약은 원자 생성이므로 `배치를 만들지 못했습니다`로 표시한다.
- 오류 원인과 입력 유지 후 `다시 시도`를 제공한다.

### 9.6 작업 센터 구조

상단:

- `전체`, `실행 중`, `주의 필요`, `검수 대기`, `완료` Filter
- 최근 업데이트 시각
- 연결 상태

배치 카드:

- 배치명과 생성 시각
- 현재 개정판
- SSOT 잠금 요약
- `성공 5 · 실행 중 1 · 실패 1`
- Count 기반 Progress Bar
- `배치 열기`
- 실패가 있으면 `실패한 1개 다시 실행`

배치 상세:

```text
화이트 제품 에셋 7종
REV-001 · 실제품 SSOT 8장 · 자동 병렬 실행 ×4

[전체 7] [대기 0] [실행 1] [QA 2] [검수 3] [실패 1]

Node cards...
```

진행률은 Terminal Node 수 또는 현재 단계 수를 기반으로 한다. 실행기가 실제 진행률을 제공하지 않는 동안 `67% 생성 중` 같은 가짜 수치를 표시하지 않는다.

### 9.7 AI Node Card Anatomy

각 카드에는 다음을 일관된 순서로 표시한다.

1. 사용자용 상태 아이콘과 라벨
2. 결과가 있으면 Thumbnail, 없으면 역할 Placeholder
3. 에셋명과 역할
4. 현재 단계: `대기`, `AI 생성`, `파일 등록`, `QA`, `검수`, `승인`
5. 입력 근거: `실제품 SSOT 5장 사용`
6. 마지막 업데이트 시각
7. 상태별 Primary Action
8. 더보기: 프롬프트, 실행 정보, 시도 이력

상태별 행동:

| 상태 | Primary | Secondary |
| --- | --- | --- |
| 준비 | 제작 시작 | 설정 보기 |
| 대기 | 없음 | 대기 취소 |
| 생성 중 | 진행 보기 | 취소 요청은 지원될 때만 |
| QA 대기 | 결과 미리보기 | 실행 정보 |
| 검수 필요 | 검수·비교 | 수정 요청 |
| 승인 | 에셋에서 보기 | 이력 |
| 실패 | 다시 실행 | 오류 상세 |
| 취소 | 다시 대기열 등록 | 이력 |
| 차단 | 문제 해결 | 입력 근거 보기 |

### 9.8 AI Node 상세

상단 Summary:

- 이름, 역할, 상태
- 배치와 개정판
- 결과 Thumbnail
- Primary Action

Tab 또는 Section:

- `진행`: 단계 Timeline과 시각
- `입력`: SSOT 참조, 사용자 프롬프트, 잠긴 제품 필드
- `결과`: 파일, 크기, 해시, 에셋 버전
- `QA`: 점수, 하드 실패, 경고, 증거
- `실행 이력`: 시도 번호, 실행기, 시작·종료, 오류

프롬프트는 기본 읽기 전용이다. 수정은 기존 시도를 바꾸지 않고 `프롬프트 수정 후 새 버전`으로 이어진다.

### 9.9 사용자용 상태 모델

내부 Job 상태와 Asset 상태를 한 단계로 오해하지 않게 합성 상태를 사용한다.

| 사용자 상태 | 내부 근거 | 의미 |
| --- | --- | --- |
| 준비 필요 | Preflight 차단 | 입력 수정 필요 |
| 대기 | Job `queued` | 실행 순서 대기 |
| 생성 중 | Job `running` | AI 생성 또는 파일 등록 |
| QA 대기 | Job `completed` + Asset `qa_pending` | 생성됐지만 판정 전 |
| 검수 필요 | Asset `review_ready` | QA 근거를 보고 사용자 결정 필요 |
| 조건부 채택 | 사용자 Override + QA 미통과 | 현재 후보 선택, 하드 게이트는 유지 |
| 승인 | Asset `approved` + QA 통과 | 조립 후보로 사용 가능 |
| 실패 | Job `failed` | 해당 시도 실패, 다른 Node는 유지 |
| 취소 | Job `cancelled` | 다시 등록 가능 |
| 이전 버전 | Asset `superseded` | 이력 보존, 현재 사용 안 함 |

`조건부 채택`은 녹색 승인이 아니다. 경고색과 `조립 전 QA 해결 필요`를 함께 표시한다. 제품 동일성 하드 실패는 사용자 판단으로 선택할 수 있어도 조립과 게시 단계에서 계속 차단한다.

### 9.10 재시도

개별 재시도:

- 기존 Node와 입력을 유지
- 새 `실행 시도`를 추가
- 이전 오류를 보존
- 성공 결과가 이미 등록된 Node는 중복 재시도하지 않음

배치 재시도:

- `실패한 2개 다시 실행`
- 실패·취소 Node만 선택
- Preflight를 다시 수행
- 원본 배치 안에 새 시도로 남기거나 파생 배치로 연결

프롬프트 수정 재시도:

- `같은 입력으로 다시 실행`과 구분
- 수정 내용을 확인
- 새 에셋 버전으로 등록
- 이전 후보는 삭제하지 않음

현재 HTTP 인터페이스에는 일괄 재시도와 시도 이력 계약이 없으므로 목표 구현에서 추가한다.

### 9.11 취소

- 대기 Node는 즉시 취소 가능
- 실행 중 Node는 실행기가 협력 취소를 지원하기 전까지 강제 취소 버튼을 노출하지 않음
- 지원 시 문구는 `취소 요청`이며 이미 생성된 결과가 등록될 수 있음을 설명
- 배치 전체 취소는 대기 Node만 취소하고 완료 결과는 보존

### 9.12 오류 UX

오류 메시지 구조:

1. 무엇이 실패했는가
2. 성공한 작업은 안전한가
3. 사용자가 지금 할 수 있는 행동
4. 필요할 때만 기술 세부 정보

예:

```text
히어로 이미지 제작에 실패했습니다.
같은 배치의 다른 6개 결과와 기존 승인본은 그대로 유지됩니다.

원인: 로컬 AI 실행기 응답이 중단되었습니다.
[같은 입력으로 다시 실행] [실행 정보 보기]
```

오류 분류:

| 분류 | 사용자 문구 | 행동 |
| --- | --- | --- |
| 입력 차단 | SSOT 잠금이 현재 개정판과 다릅니다 | 새 개정판에서 SSOT 확인 |
| 실행기 불가 | 로컬 AI 실행기를 시작할 수 없습니다 | 상태 확인, Queue 등록 |
| 생성 실패 | 이미지 제작에 실패했습니다 | 개별 재시도 |
| 결과 무결성 | 유효한 PNG 결과가 아닙니다 | 재시도, 실행 정보 |
| 파일 등록 실패 | 결과를 프로젝트에 저장하지 못했습니다 | 저장 공간·경로 확인 |
| QA 하드 실패 | 실제품과 다른 부분이 발견됐습니다 | 증거 보기, 수정 버전 |
| 연결 중단 | Studio 연결이 끊겼습니다 | 자동 재연결, 수동 새로고침 |

원시 Stack Trace, PID, 내부 경로는 `기술 세부 정보` 안에 둔다.

### 9.13 알림

- Node 하나의 정상 완료마다 Toast를 남발하지 않는다.
- 배치 전체 제작 종료, 첫 실패, 사용자 검수 준비 시점만 알린다.
- 작업 센터를 열고 있을 때는 Toast 대신 목록 상태를 갱신한다.
- SSE 재연결 중에는 상단 저장 상태에 `다시 연결 중`을 표시한다.
- 배치 완료 알림은 `제작 완료`와 `검수 필요`를 함께 말한다.

예: `에셋 7개 제작이 끝났습니다. 6개는 검수 준비, 1개는 다시 실행이 필요합니다.`

## 10. AI 업데이트 방향

### 10.1 Prompt Compiler

사용자가 자유 텍스트만 작성하게 두지 않고 다음 순서로 최종 실행 프롬프트를 구성한다.

1. 제품 사실 SSOT와 잠긴 라벨·색상
2. 변경 금지 필드
3. 에셋 역할과 사용 목적
4. 사용자가 원하는 장면·변화
5. 금지 요소와 출력 조건

UI는 최종 프롬프트 전체보다 `유지할 것`, `만들 것`, `금지할 것`을 먼저 보여준다. `최종 실행 지시 보기`에서 합성 결과를 확인할 수 있다.

### 10.2 Reference Selection

현재 실행기는 최대 5개의 참조 이미지를 사용한다. 실제품 SSOT가 더 많을 때 AI가 어떤 5장을 선택했는지 Node 입력에서 표시한다.

목표:

- 역할에 맞는 정면·측면·라벨·구조 사진 자동 추천
- 사용자가 추천된 참조를 실행 전에 확인
- 참조 교체 시 새 시도로 기록
- 참조가 부족하면 Preflight 경고

### 10.3 Model·Executor Routing

사용자는 기본적으로 실행기 구현명을 선택하지 않는다.

- 기본: `자동 병렬 실행`
- 대안: `대기열만 등록`
- 진단: 실행기 이름, 버전, Provider, 동시성

모델 또는 실행기 교체는 Generation Adapter seam 뒤에서 처리한다. UI의 Node·배치 상태와 승인 흐름은 바뀌지 않아야 한다.

### 10.4 AI QA

AI QA는 다음을 분리한다.

- 기계 검사: 파일, 형식, 크기, 해시, 누락
- 제품 동일성: 형태, 비율, 라벨, 재질, 부품 위치
- 디자인 일관성: 조명, 색감, 타이포, 페이지 리듬
- 사용자 판단: 승인, 보류, 반려, 조건부 채택

하드 실패와 디자인 경고를 한 목록에 섞지 않는다. 하드 실패는 구체적 증거와 해결 행동을 요구한다.

### 10.5 AI 행동 제한

AI는 다음을 실행할 수 없다.

- SSOT 잠금 확인 체크
- 사용자 조건부 채택
- 에셋 승인
- 조립 확정
- 최종 사용자 승인
- 게시용 내보내기

AI가 제안할 수는 있지만 최종 버튼은 사용자 입력으로만 동작한다.

### 10.6 재현성과 Provenance

각 결과는 다음 정보를 보존한다.

- 프로젝트와 개정판
- 배치와 AI Node
- 실행 시도
- SSOT 참조 ID와 해시
- Prompt Compiler 버전과 최종 프롬프트
- 실행기·Provider·크기
- 결과 파일 해시
- QA 보고서
- 사용자 결정

## 11. 목표 아키텍처

### 11.1 시스템 흐름

```text
Studio UI
  │ HTTP Interface + SSE
  ▼
Local Studio Server
  ├─ Project Store
  ├─ Batch Orchestrator
  ├─ AI Node Registry
  ├─ Asset Registry
  ├─ Approval Gate
  ├─ Dependency Graph
  ├─ Assembly Lock
  └─ Event Stream
       │
       ▼
Worker Pool
  ├─ ImageGen Adapter → god-tibo-gpt-image2-skill 구현
  ├─ HyperFrames Adapter → 결정적 모션 렌더 구현
  └─ QA Adapter → Codex visual QA 구현
```

브라우저는 실행기 세부 명령과 자격 증명을 알지 않는다. 배치와 Node 요청을 구조화하고 Local Studio Server가 검증·저장·실행한다.

`자동 병렬 실행`과 `대기열만 등록`은 생성 Adapter가 아니라 Batch Orchestrator의 Dispatch 정책이다. 대기열 등록은 같은 Node 계약을 저장하되 Worker Pool을 바로 시작하지 않는다.

### 11.2 깊은 Module과 Interface

#### Project Store

```text
load()
mutate(command)
snapshot()
```

원자 저장, 스키마 버전, 이벤트 이력과 복구는 구현 안에 숨긴다.

#### Batch Orchestrator

```text
createBatch(request)
start(batchId)
retryFailed(batchId)
cancelQueued(batchId)
snapshot(batchId)
```

Node 생성, 중복 역할 검사, 동시성, 집계 상태와 부분 실패 격리는 구현 안에 숨긴다.

#### AI Node Runner

```text
run(nodeId)
retry(nodeId, mode)
cancel(nodeId)
```

실행 시도, 입력 고정, 결과 등록과 오류 정규화는 구현 안에 숨긴다.

#### Approval Gate

```text
evaluate(assetVersion)
approve(assetVersion, decision)
canAssemble(revision)
```

QA 통과, 하드 실패, 사용자 결정, 조건부 채택과 필수 역할 계산을 한곳에 둔다.

#### Dependency Graph

```text
affectedBy(assetVersion)
```

에셋 → HyperFrames → GIF → HTML 섹션의 영향 범위를 계산한다.

#### Generation Adapter seam

생성 대상과 실행 계약이 실제로 달라지는 seam이다.

- ImageGen Adapter
- HyperFrames Adapter

현재 ImageGen Adapter의 유일한 구현은 로컬 `god-tibo-gpt-image2-skill` Worker다. Studio UI와 Batch Orchestrator는 하위 패키지 명령 형식이나 로그인 방식을 직접 알지 않는다.

### 11.3 현재 계약과 목표 계약

현재는 각 Job의 `executor.batchId`로 묶음을 추론한다. 목표에서는 Batch를 첫 번째 클래스 기록으로 승격한다.

목표 Batch:

```json
{
  "id": "batch-...",
  "revisionId": "rev-001",
  "name": "화이트 제품 에셋 7종",
  "sourceLockId": "ssot-lock-...",
  "nodeIds": ["node-1", "node-2"],
  "execution": {
    "dispatch": "auto-start",
    "adapter": "imagegen",
    "implementation": "god-tibo-gpt-image2-skill",
    "concurrency": 8,
    "size": "1024x1536"
  },
  "status": "running",
  "summary": {
    "total": 7,
    "queued": 2,
    "running": 1,
    "qaPending": 1,
    "reviewReady": 2,
    "failed": 1,
    "approved": 0
  }
}
```

목표 AI Node:

```json
{
  "id": "node-...",
  "batchId": "batch-...",
  "type": "image-generation",
  "target": {
    "name": "화이트 루즈핏 히어로",
    "role": "hero-product",
    "required": true
  },
  "sourceRefs": ["ssot-user-front", "ssot-user-label"],
  "promptVersion": 1,
  "status": "qa_pending",
  "attemptIds": ["attempt-1"],
  "result": {
    "assetId": "hero-product",
    "version": 1,
    "sha256": "..."
  }
}
```

목표 실행 시도:

```json
{
  "id": "attempt-1",
  "nodeId": "node-...",
  "number": 1,
  "adapter": "imagegen",
  "implementation": "god-tibo-gpt-image2-skill",
  "status": "completed",
  "startedAt": "...",
  "completedAt": "...",
  "error": null
}
```

### 11.4 상태 불변식

- Batch 생성은 모든 Node가 만들어지거나 아무것도 만들어지지 않는 원자 작업이다.
- 한 Node 실패는 다른 Node 상태를 바꾸지 않는다.
- 재시도는 이전 실행 시도를 덮어쓰지 않는다.
- 생성 결과는 항상 새 에셋 버전이다.
- Job 완료와 QA 완료는 별도 상태다.
- 조건부 채택은 하드 실패를 제거하지 않는다.
- 미처리 Node 또는 하드 실패가 있으면 조립할 수 없다.
- 조립 뒤 에셋·모션 Node의 변경 Interface는 닫힌다.
- 새 개정판은 기존 조립 잠금과 승인 이력을 보존한다.

### 11.5 Event Stream

목표 이벤트:

```text
batch.created
batch.started
node.queued
node.started
node.output_registered
node.failed
node.cancelled
qa.started
qa.completed
asset.review_ready
asset.approved
batch.attention_required
batch.production_completed
```

이벤트는 UI 알림용이면서 새로고침 뒤 상태를 재현할 수 있는 기록이어야 한다. UI는 이벤트만 믿지 않고 서버 Snapshot으로 최종 상태를 복원한다.

## 12. Visual Design Direction

### 12.1 성격

- 전문 크리에이티브 운영 도구
- 차분하고 정확한 화면
- 높은 정보 밀도, 명확한 위계

### 12.3 상태 색상

- Blue: 선택, 진행, Primary Action
- Green: QA 통과 후 사용자 승인 완료
- Amber: QA 대기, 경고, 조건부 채택, 사용자 검수 필요
- Red: 실행 실패, 하드 실패, 차단
- Gray: 대기, 취소, 이전 버전, 읽기 전용

모든 색상은 아이콘과 텍스트 상태를 동반한다.

### 12.4 Typography와 밀도

- 기본: Pretendard, Malgun Gothic, system-ui
- Body: 14px
- 보조 정보: 최소 11px 권장
- 상태·시간·ID 같은 Metadata만 10px 허용
- 사용자 행동과 오류 본문은 12px 미만으로 내리지 않음
- 카드 Radius 8~10px
- 8px spacing grid

현재 UI의 9~10px 보조 텍스트는 AI Node 오류와 QA 근거를 읽기에는 작다. 목표 설계에서는 중요한 상태·오류·행동 문구를 12px 이상으로 올린다.

### 12.5 Motion

- Panel: 180~220ms
- 상태 전환: 150~180ms
- Skeleton은 느린 Pulse, 과도한 Shimmer 금지
- 배치 완료 시 축하 Animation 금지
- 오류 카드 흔들기 금지
- `prefers-reduced-motion` 지원

## 14. 접근성·반응형·복구

### 14.1 접근성

- 모든 상태는 색상 외 텍스트와 아이콘 제공
- 키보드로 Stage, Batch, Node, Version 이동
- Dialog 열림 시 Focus Trap, 닫힘 시 Trigger로 Focus 복원
- 실행 상태 변경은 `aria-live="polite"`

- 이미지 비교에는 원본·후보 대체 텍스트

## 17. 구현 수락 기준

- 배치 시작 전 현재 개정판과 잠긴 SSOT를 확인할 수 있다.
- 완성·진행 중 역할은 기본 제작 대상에서 제외되고 이유가 표시된다.
- 배치 생성은 선택한 Node 전체에 대해 원자적으로 처리된다.
- 배치와 각 AI Node 상태를 동시에 이해할 수 있다.
- AI Node 하나의 실패가 다른 성공 결과를 숨기거나 무효화하지 않는다.
- 작업 센터를 닫아도 상단바와 결과 Board에서 진행 상태를 확인할 수 있다.
- 실행기가 실제 Progress를 주지 않을 때 가짜 퍼센트를 표시하지 않는다.
- 생성 완료, QA 대기, 검수 필요, 조건부 채택, 승인 상태가 구분된다.
- 실패한 Node만 다시 실행할 수 있고 이전 시도 이력이 남는다.
- 프롬프트 수정은 기존 결과를 덮어쓰지 않고 새 버전을 만든다.
- AI Node 상세에서 SSOT 참조, 프롬프트, 실행기, 결과 해시와 QA를 확인할 수 있다.
- 하드 실패는 조건부 채택 뒤에도 조립과 게시를 차단한다.
- AI는 승인·조립·게시 행동을 대신 실행할 수 없다.
- 조립 뒤 변경은 새 개정판으로만 이어진다.
- 새로고침과 SSE 재연결 뒤에도 배치·Node 상태가 복원된다.
- 상태는 색상만이 아니라 텍스트·아이콘·수치로 전달된다.
