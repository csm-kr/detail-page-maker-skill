# ADR-0009 — G8(모션)과 G9(조립)를 병렬로 돌리고 G10을 배리어로 둔다

**상태** 채택 · 2026-08-05

## 맥락

사용자 질문 — "이걸 시간을 위해 병렬로 처리가능해?"

의존 그래프를 다시 보니 병렬로 벌 수 있는 곳이 예상과 달랐다.

| 후보 | 결과 |
| --- | --- |
| G4 목업 (23분, 최대 구간) | **불가.** 병렬 탭은 다른 대화가 되어 톤이 갈린다. 실측: 한 턴 10장은 2분 15초로 빠른데 정렬·배경·아이콘이 갈렸다 |
| G6 스틸 생성 | 이미 최대. god-tibo가 32 workers 동시 |
| G1 ∥ G2 | 가능. 입력이 다르다. ~8분 |
| **G8 ∥ G9** | **가능. 이것이 새로 찾은 것** |

원래 계획은 `G9 선행 = G7, G8`이었다. 그런데 G9가 실제로 필요한 것은
`page-plan.md`(G7)이고, **GIF 파일의 존재는 G10의 `strict-media`가 잡는다.**
G9는 HTML에 GIF 경로를 쓰지만 그 시점에 파일이 있어야 하는 것은 아니다.

## 결정

```text
G7 ─┬─ G8 ─┬─ G10 → G11
    └─ G9 ─┘
```

- `G9 선행 = G7` (G8을 뺀다)
- `G10 선행 = G8, G9` — **G10이 배리어다.** 양쪽 산출물을 함께 봐야
  `ASSET_MISSING`을 잡는다.
- G8의 검사 중 "자막 용어 ⊆ 페이지 용어 집합"은 HTML이 아니라 `page-plan.md`(G7)를
  기준으로 한다. 그래야 G9와 독립이다.
- 절약 ~6분. G8 10분 / G9 6분이므로 직렬 16분이 병렬 10분이 된다.

### 함께 정하는 것 — 게이트 내부 fan-out

**게이트 간 병렬보다 게이트 내부 병렬이 이득이 크다.**

| 단계 | 내부 병렬 | 현재 |
| --- | --- | --- |
| G6 스틸 | 32 workers 동시 | 이미 최대 |
| G8 GIF | 10개를 별도 프로세스로 동시 렌더 | **아직 순차 — 여기가 남은 이득** |
| G4 목업 | 불가 (톤) | 4장씩 한 대화 유지 |

`run --parallel`은 **선행 게이트가 `○`인 단계만** 동시에 띄운다.

## 결과

**좋아지는 것.** GIF 렌더가 임계경로에서 빠진다. G1∥G2와 합쳐 ~14분.

**나빠지는 것.** G9가 "GIF가 없는 상태의 HTML"을 만들 수 있다. 반쪽 완성본이 남는
것처럼 보이지만 **G10이 통과하지 않으면 `report`가 exit 1**이므로 완료로 오인될 수
없다. 이것이 배리어를 G10에 두는 이유다.

**주의.** 2회차에 스틸을 백그라운드로 앞당긴 것이 G5 누락의 직접 원인이었다.
병렬 자체가 위험이 아니라 **선행 검사 없는 병렬**이 위험이었다. 그래서 병렬은
`gates.mjs`가 선행을 확인한 뒤에만 허용한다.

## 기각한 대안

| 대안 | 기각 이유 |
| --- | --- |
| G8 → G9 직렬 유지 | 안전하지만 6분을 버린다. G10 배리어로 안전성이 확보된다 |
| G9가 GIF 자리표시자를 넣고 나중에 교체 | 자리표시자가 남을 위험. 지금은 경로만 쓰고 파일은 G10이 검사한다 |
| G4를 탭 4개로 병렬 | 톤이 갈린다. 실측으로 확인된 사항이다 |
| G6·G8을 G4 진행 중에 미리 시작 | 2회차 실패의 재현이다. G5 주입 전 스틸은 무드가 빠진다 |
