## 시작 전 — 설치·환경

### 1. `init` 의 hyperframes 벤더링이 Windows 에서 항상 실패한다 · 고침

`lib/vendor.mjs` 가 `shell` 없이 `npm.cmd` 를 `spawnSync` 했다. Node 18.20/20.12 이후
Windows 는 이걸 거부한다(EINVAL). 25ms 만에 죽고 `installed: false` 로 조용히 넘어가서
`init` 은 "성공"처럼 보이는데 G8 에서야 드러난다.

- 증상: `hyperframes  project-local motion/ (미설치)  ✗`
- 원인: `spawnSync(npm, args, {...})` — Windows 에서 `.cmd` 는 `shell: true` 필요
- 고침: `shell: process.platform === "win32"` 추가. 인자가 전부 고정 문자열이고 경로는
  `cwd` 옵션으로 가므로 셸이 해석할 입력이 없다
- 테스트: `init.test.mjs` "npm 을 실제로 띄운다" — 의존성 없는 `package.json` 으로
  레지스트리 없이 런처만 검사한다

### 2. 검증된 추출기가 문서상 죽어 있었다 · 고침

`lib/extract.mjs` 는 domeggook.com → `dmk-extractor`, coupang.com → `coupang-extractor`
로 보내고 `orchestrate capture` 가 그것을 부른다. 그런데 **G1·G2 의 SKILL.md 와 거부
메시지가 `orchestrate lock --read` 만 가리켰다.** 문서대로 따르면 손으로 캡처해서
등록하게 되고 추출기는 한 번도 안 불린다 — 선택 로직 전체가 죽은 코드였다.

손 캡처에 없는 것: `ACCESS_BLOCKED` 판정, 상품번호 대조, 후기 개인정보 마스킹,
자산별 원본 다운로드, GIF 프레임 분리.

- 고침: G1·G2 SKILL.md 를 `orchestrate capture --url … --as …` 로 바꾸고,
  `lock --read` 는 추출기 없는 호스트용 폴백으로 내렸다. 두 `check.mjs` 의 거부
  메시지도 같이 바꿨다 — 막힌 사람이 실제로 읽는 곳이 거기다
- 테스트: `extract.test.mjs` "단계 문서가 추출기 경로로 보낸다" + 각 게이트의
  "추출기 경로를 알려준다"

## 회차 진행 중

### 4. G1 · "해야 하는 것" 목록이 두 벌이라 갈렸다 · 고침

`SKILL.md` 를 고쳤는데 `node scripts/run.mjs` 는 옛 문구를 출력했다. 같은 체크리스트가

레포 자신의 원칙("같은 표를 두 문서에 적으면 갈린다 — ARCHITECTURE 한 곳만")에
정면으로 걸린다. 게이트 표에는 그 원칙을 적용했는데 단계 체크리스트에는 안 했다.

- 고침: G1·G2 의 `run.mjs` 를 `SKILL.md` 와 맞췄다
- 테스트: `purity.test.mjs` "run.mjs 의 체크리스트가 SKILL.md 와 갈리지 않는다" —
  최상위 `- ` 항목을 순서까지 대조한다. `checklist()` 가 없는 게이트(G5·G6·G8·G9·G10·G11)는
  스크립트가 직접 산출물을 쓰는 쪽이라 제외한다
- 남은 빚: 근본 해법은 `run.mjs` 가 `SKILL.md` 를 읽어 목록을 만드는 것이다. 지금은
  테스트로 갈림만 막았다 — 11개 게이트를 건드리는 리팩터는 이 회차 범위 밖으로 뒀다

### 5. G2 의 캡처가 G1 을 무효화한다 · 못 고침 (설계 이슈)

`G1 --pass` 로 통과시킨 뒤 `capture --as reference` 를 돌렸더니 G1 이 `⚠ STALE` 로
돌아갔다. G2 를 통과시켜도 "다음 G1" 이라고 나온다.

원인: `gates.mjs` 에서 G1 과 G2 가 **둘 다** `inputs: ["work/inputs.lock.json"]` 을
선언한다. 그런데 `capture` 는 어느 게이트의 것이든 그 **한 파일에** 항목을 추가한다.
그래서 G2 가 자기 일을 하면 G1 의 입력 해시가 바뀌고, G1 이 무효화된다.

무효화 전파 자체는 맞게 동작한다 — 틀린 것은 **입력 granularity** 다. 파일 단위로
해싱하니 "내 입력이 바뀌었다" 와 "남의 항목이 추가됐다" 를 구분하지 못한다.

이 레포는 같은 유형을 이미 한 번 풀었다. ADR 0005 — "G4 의 입력이 초안이므로 G5 가
같은 파일을 고치면 G4 가 무효화되고 서로를 되돌린다" → 초안/발행을 파일로 쪼갰다.
공유 `inputs.lock.json` 에는 그 해법이 적용되지 않았다.

- 실제 영향: 캡처가 있는 게이트가 두 개(G1·G2)라서 최소 1회는 반드시 헛돈다.
  순서를 어떻게 잡아도 나중에 캡처하는 쪽이 먼저 통과한 쪽을 깬다
- 이번 회차 처리: G1 의 `check` 를 다시 돌려 통과시켰다. 사실이 바뀐 게 아니라
  판정이 다시 참이므로 우회가 아니다. 다만 예산 8분짜리 게이트를 근거 없이
  두 번 지나가게 만든다
- 권고: 게이트별 입력을 `work/inputs.lock.json#captures.supplier` 처럼 **경로로
  좁히거나**, 캡처를 `input/bundles/<label>/manifest.json` 단위로 직접 선언하게 한다.
  후자가 이 레포의 기존 방식(자산별 해시)에 더 가깝다
- 안 고친 이유: 무효화 엔진의 해싱 단위를 바꾸는 일이라 회차 중간에 손대면 이미
  통과한 게이트 상태가 통째로 흔들린다. 회차 밖에서 할 일로 남긴다

### 8. `parseBackground` 가 설명 문장을 키워드로 긁어간다 · 우회 (파서 버그)

`## 배경` 절에 설명을 곁들였더니 주입 결과가 이렇게 나왔다.

```
배경   프롬프트에, 주입할, 배경, 장식, 키워드, 목업에서
```

`guide.mjs:28-38` 의 `parseBackground` 는 절 안의 **모든 2글자 이상 한글 낱말**을
키워드로 가져간다. 설명 문장을 쓰면 그 문장의 조사 붙은 어절이 그대로 컷 프롬프트에
주입된다. 같은 파일의 `parsePalette` 는 `- 이름 \`#HEX\`` 목록만 읽어 이 문제가 없다.

- 이번 회차 처리: `## 배경` 절에서 설명을 전부 빼고 키워드만 남겼다
- 권고: `parseBackground` 도 `parsePalette` 처럼 **목록 형식만** 읽게 한다.
  산문을 허용하면 조용히 오염되고, 오염된 채로 30개 컷 프롬프트에 들어간다
- 이 실패는 게이트를 통과한다. 검사가 "키워드가 0개가 아닌가" 만 보기 때문이다

### 9. G6 이 만든 파일 이름을 G6 이 못 찾는다 · 고침

`--publish` 가 채택한 12개 컷을 전부 `FFMPEG_FAILED 종료 코드 4294967254` 로 떨어뜨렸다.
ffmpeg 문제가 아니라 **없는 파일을 넘긴 것**이었다.

- 생성기가 쓰는 이름: `work/stills/frame-000.png` … `frame-029.png`
- 발행이 찾는 이름: `run.mjs:102` 의 `work/stills/<컷id>.png` → `cut-01.png`

같은 게이트의 두 단계가 파일명 규약을 공유하지 않는다. 오류 메시지도 ffmpeg 를 가리켜서
원인이 어긋난 곳에서 멀어진다.

- 고침: `lib/source.mjs` 의 `stillSource()` 를 만들어 **판정 기록의 `file` 을 1급으로** 쓰고,
  없을 때만 `<컷id>.png` 규약으로 되돌아간다. 판정할 때 이미 그 파일을 연 상태이므로
  경로를 가장 정확히 아는 곳이 판정 기록이다
- 경로 탈출 방어를 같이 넣었다. `selection.json` 은 사람이 쓰는 파일이라 `../` 나 절대
  경로가 들어오면 회차 밖 파일이 발행된다 — `STILL_SOURCE_OUTSIDE` 로 거부한다
- 실패 안내 문구도 바꿨다. "파일 이름을 확인해라" 가 아니라 "`file` 에 실제 경로를 적어라"
- 테스트: `g6/scripts/tests/source.test.mjs` 3개

### 10. 이미지 생성이 근거 없는 주장과 가공 브랜드를 이미지에 구워 넣는다 · 못 고침 (가장 큰 위험)

30장을 원본 해상도로 전부 열어 본 결과 **18장 탈락**했다. 그중 9장이 같은 유형이다.

| 컷 | 이미지에 박힌 것 |
| --- | --- |

나머지 탈락은 격자 인쇄 5건, 타공 개수 불일치 3건(1개 또는 6개), 구성에 없는 걸이 부품 1건.

**이것이 이 회차에서 가장 위험한 실패다.** 무독성·지속성·규격은 SSOT `unknowns` 이고,
브랜드는 아예 존재하지 않는다. 그대로 발행하면 표시광고법 문제이자 허위 표시다.

- 원인: G3 플랜의 금지어 목록(`FORBIDDEN`)과 SSOT 의 `unknowns` 가 **이미지 생성
  프롬프트까지 전달되지 않는다.** 컷 `prompt` 에는 장면만 적혀 있고 "문자를 넣지 마라",
  "브랜드·포장·인증 배지를 만들지 마라" 가 없다
- 검사도 못 잡는다. G6 의 check 는 판정 **기록**만 본다 — 이미지 픽셀은 보지 않는다.
  사람(에이전트)이 30장을 원본으로 열지 않으면 그대로 통과한다.
  즉 이 게이트는 "선별을 했는가" 는 강제하지만 "무엇을 봤는가" 는 강제하지 못한다
- 권고 1: 컷 프롬프트 조립 시 **문자·로고·포장·배지 금지 블록을 무조건 붙인다.**
  `moodBlock()` 이 배경·강조색을 붙이는 자리와 같은 곳에서 처리하면 된다
- 권고 2: `unknowns` 를 프롬프트에 부정 제약으로 주입한다. SSOT 가 "모른다" 고 한 것은

- 권고 3: 발행 전 자동 OCR 로 라틴 문자를 검출해 경고한다. 완전한 방어는 아니지만
  `NON-TOXIC` 같은 대문자 배지는 대부분 걸린다
- 안 고친 이유: 프롬프트 조립부와 생성 백엔드 계약을 바꾸는 일이라 회차 중간 범위 밖이다.

### 11. G9 빌더가 빈 껍데기를 만들고 G9 검사가 통과시킨다 · 고침 (가장 중요한 결함)

`G9 --check` 가 통과했는데 `output/detail-page.html` 은 5,963 바이트였고 이랬다.

```html
--bg-1: 옅은연두;          /* CSS 변수에 한글 키워드가 색상 값으로 */
<h2 class="head"></h2>     /* 헤드라인 8개가 전부 비어 있음 */
```

- 빌더가 `sections[].headline` `kicker` `subcopy` 를 **읽지 않는다.** 섹션 껍데기만 찍는다
- `parseBackground` 로 뽑은 한글 키워드를 `--bg-N` 색상 변수에 그대로 넣는다.
  `background: var(--bg-1)` 은 무효값이라 렌더에 아무 영향이 없다 (이슈 8의 하류 결과)
- 미디어 참조 0개. 발행한 이미지 12장·GIF 10개를 하나도 걸지 않는다

**그런데 검사가 통과했다.** `check.mjs` 는 "HTML 의 한글이 전부 플랜에서 왔는가" 만 본다.
빈 페이지는 플랜 밖 문자열이 0건이므로 **완벽하게 통과한다.** 방향이 하나뿐이었다.

이 레포의 서사가 "45개 테스트가 전부 통과했는데 13단계가 누락돼 있었다 — 전부 존재
검사였기 때문이다" 인데, G9 에서 같은 유형이 그대로 재현됐다. 존재가 아니라 내용을
본다는 원칙이 **한 방향으로만** 적용돼 있었다.

- 고침: `g9/check.mjs` 에 반대 방향 검사를 넣었다 — 플랜의 각 `headline` 이 HTML 에
  실제로 들어갔는지 본다. 넣자마자 8개 섹션 전부를 잡아냈다
- 테스트: `g9/tests/check.test.mjs` "헤드라인이 비어 있는 껍데기를 통과시키지 않는다"
- 빌더 자체는 고치지 않았다. 이번 회차의 HTML 은 플랜을 근거로 직접 조립했고,
  새 검사와 기존 검사(플랜 밖 문자열 0건 · 폭 780px · hex 는 :root 에만 · 구성 요소
  클래스 · 인라인 SVG · 앵커 해시)를 전부 통과시켰다
- 권고: 빌더가 플랜의 `kicker`/`headline`/`subcopy`/`body`/`table`/`cautions`/`footnote`
  를 실제로 렌더하게 고친다. 그리고 `--bg-N` 에 색이 아닌 값이 들어가면 거부한다

### 12. 엄격한 선별과 수량 하한이 정면으로 충돌한다 · 못 고침 (회차가 여기서 멈춤)

`G10 --check` 가 `STILL_COUNT_OUT_OF_RANGE count=12` 로 막힌다.
`lean-html-qa.mjs:98` 이 발행 이미지 **28~32장**을 요구하고 `strictMedia: true` 가
`g10/run.mjs:21` 에 하드코딩돼 있다.

그런데 G6 은 "30장 만들어 30장 그대로 발행한 것을 잡는다. 선별이 통과 조건이다" 라고
선언한다. 이번 회차에서 규칙대로 판정하니 18장이 탈락했고 12장이 남았다.
**선별을 제대로 할수록 G10 을 통과할 수 없다.**

- 빠져 있는 것: **재생성 루프**. `selection.json` 에 `regen_job` 18개를 다 적었는데
  그것만 다시 굽는 경로가 없다. `run.mjs` 에는 `--publish` 플래그뿐이고,
  다시 돌리면 30장을 전부 새로 만들어 이미 채택한 12장까지 날아간다
- 그래서 실제로는 두 선택지밖에 없다 — 30장을 통째로 다시 만들어 전량 재판정하거나,
  판정을 느슨하게 해서 하자 있는 컷을 채택하거나. 후자를 하면 게이트가 무의미해진다
- 이번 회차 처리: **하지 않았다.** 임계값을 낮추거나 탈락분을 채택으로 바꾸는 것은
  이 레포가 금지한 탈출구다(`--force 없음`, "탈출구를 주면 그 길로 간다").
  회차는 G10 에서 멈춘 상태로 둔다
- 권고 1: `run.mjs --regen` 을 만든다. `selection.json` 의 `decision: "reject"` 항목만
  `regen_job` 프롬프트로 다시 굽고, 채택분은 손대지 않는다. 그러면 선별→재생성→재판정이
  실제 루프가 된다
- 권고 2: 그 루프가 생기기 전까지는 `strictMedia` 의 하한을 **플랜의 컷 수가 아니라
  채택 수 기준**으로 본다. 지금은 "30장을 만들었는가" 를 묻는데 물어야 할 것은
  "발행한 것이 전부 판정을 통과했는가" 다
- 권고 3: 이슈 10(프롬프트에 문자 금지 블록 없음)을 먼저 고쳐야 재생성이 의미가 있다.
  지금 그대로 다시 구우면 같은 이유로 또 탈락한다
