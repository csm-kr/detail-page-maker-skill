# 완주 run 실행 플로우

실제로 끝까지 완주한 제작 run에서 **실행 순서와 판단 방식만** 뽑은 문서다.
특정 상품의 공급처·경쟁작·사양·카피·좌표·팔레트는 담지 않는다. 그 값들은
매 run마다 근거에서 새로 확정한다. 이 문서는 그 값을 **어떤 순서로 어떻게
확정했는지**만 규정한다.

핵심 원칙 네 가지가 전 구간에 반복된다.

1. 만들기 전에 읽고 판독한다. 요약·기억·검색으로 대체하지 않는다.
2. 실패는 숨기지 않고 코드·원인·재시도 결과를 그대로 남긴다.
3. 근거가 없으면 만들지 않고, 만들 수 없는 것은 대체 방식을 정해 명시한다.
4. 통과한 산출물은 재생성하지 않고 실패 member와 그 descendant만 다시 돌린다.

## 0. 환경 확인

| 순서 | 행동 | 판단 기준 |
| --- | --- | --- |
| 0.1 | 정본 문서 통독 | `content-contract.md`, `workflow.md` 먼저. 이후 작업별 reference를 필요한 시점에 추가 |
| 0.2 | `doctor` | Node·HyperFrames·browser-harness·ffmpeg·번들 스킬 선언/잠금/설치 수 일치 |
| 0.3 | `agent-capacity` | `dispatch_ready` 확인 |

`dispatch_ready: false`면 봉인형 Orchestrator의 생산자≠검증자 요건을 만들 수 없다.
이때 게이트 CLI를 흉내내거나 session ID를 지어내지 않는다. **같은 콘텐츠 계약과
같은 runner를 단일 세션에서 순서대로 직접 실행·검증하고, 게이트를 쓰지 않았다는
사실을 최종 보고에 그대로 밝힌다.**

## 1. 입력 확인 — 상품 정체 확정

HTML보다 먼저 "이 물건이 정확히 무엇인가"를 닫는다.

1. 사용자가 준 실제 사진을 **전부 육안 판독**한다. 겉면·안쪽·구성·좌우 구분·부품을
   글로 적어 확정한다.
2. 폴더명·파일명·첫인상으로 품목을 단정하지 않는다. 공급처 원문 title과 교차 검증한다.
3. 공급처 추출기를 돌린다. 실패하면:
   - 실패 코드와 원인을 그대로 보존한다.
   - partial staging에 남은 **실제 응답 bytes**로 계속 진행할 수 있는지 판단한다.
   - manifest 없는 partial 번들임을 로그에 명시하고, 누락 자산이 상품 정체에
     영향을 주는지 따로 판정한다.
4. 원문을 같은 디코더·정제 로직으로 직접 파싱해 확정한다.
   - 상품명 / 이미지 사용권 표기 / **후기 수**
   - 후기 0건이면 후기 섹션을 만들지 않기로 그 자리에서 확정한다.
   - 사용권 표기는 관찰값으로만 기록하고 판매용 사용권으로 단정하지 않는다.
5. 세로로 긴 상세 이미지는 일정 픽셀 단위로 잘라 **조각 전부를 육안 판독**한다.
6. 여기서 다음 세 가지를 닫는다.
   - 상품정보고시 표 (표기명·사이즈·색상·소재·제조국·구성)
   - 제조사 문구 원문 (`manufacturer_claim`)
   - **`verified_efficacy` 건수** — 0건이면 수치·시험·개선율 주장 전면 금지로 확정

## 2. 경쟁 기준작 수집

1. 기준작 추출기를 먼저 돌린다. 필수 식별자가 없어 실패하면 평문 fetch로 우회하지
   않는다(차단됨).
2. 브라우저 harness로 페이지를 열어 DOM에서 식별자를 추출한다. **브라우저 lane은
   전역 1개로 직렬 운용**하고, 이 구간에는 다른 브라우저 작업을 겹치지 않는다.
3. 식별자를 붙여 재수집하고 status·수집 수·validation error·manifest 해시를 기록한다.
4. 기준작 상세 이미지와 원본 컷을 **전부 육안 판독**해 판매 논리 **순서**를 뽑는다.
   자산·카피는 복제하지 않고 순서와 증명 방식만 가져온다.
5. 후기를 평점 분포로 집계하고 **저평점 원문을 읽는다.**
   - 반복되는 불편을 카테고리 단위로 묶는다(연구 전용, 우리 제품 주장으로 전용 금지).
   - **저평점이 기준작의 구조에서 나오고 우리 제품 구조가 다르면, 그 지점이 관찰
     가능한 차별점이 된다.** 이 대응을 pain↔solution 1:1 설계의 축으로 삼는다.

## 5. G1 기획 — HTML보다 먼저

**HTML을 먼저 만들지 않는다.** 아래 문서를 확정한 다음에 소재를 만든다.

| 파일 | 담을 것 |
| --- | --- |
| `COMMERCIAL.md` | SSOT 표, 제품 불변 조건, claim 경계(fact ID), 기준작 판매 논리 대조표, pain/solution, 비교, 사양, FAQ, 금지 목록 |
| `GIF.md` | motion 다양성 표(목적·카메라·핵심 변화·전환·강조 그래픽·pattern·template) + 개별 brief |
| `DESIGN.md` | 아키타입 바인딩, 팔레트, 타이포 스케일, 줄바꿈 규칙, 밀도 곡선, motion 배치 규칙 |
| `BUYER-JOURNEY.md` | 섹션별 (고객 질문 / 한 메시지 / 주 시각 / 정지·모션 / 다음 이유) + coverage 검증표 |

### 5.1 제품 불변 조건

모든 생성 컷에 공통으로 주입할 조건을 **먼저 글로 확정**한다. 형태·개방부·색·부품
위치·좌우 구분·개수, 그리고 **금지 요소**(로고·인쇄 문구·없는 부품)를 함께 적는다.

### 5.2 pain ↔ solution 1:1

| 열 | 내용 |
| --- | --- |
| pain | §2.5에서 뽑은 카테고리 불편 |
| 공개 말풍선 | 고객 어투 한 줄 |
| solution | 관찰 가능한 구조로만 대응 |
| 근거 유형 | `observable_structure` / `manufacturer_claim` / `verified_efficacy` |

### 5.3 근거 없는 필수 항목 처리

필수 motion이 요구하는데 공급처에 근거가 없으면(예: 실측 치수 미표기)
**숫자를 만들어내지 않는다.** 측정 대상 자체를 근거 있는 것으로 바꾸고, 무엇을
왜 바꿨는지 기록한다.

## 6. G2 이미지 배치

### 6.1 SSOT anchor 준비

공급처 상세에서 geometry 컷을 잘라 anchor로 쓴다.

- **문자가 들어간 영역은 배제**한다.
- 타사 로고가 보이는 컷은 잘라놨더라도 폐기한다.
- 제품 단독 컷은 실제 사진을 Image 1로, 착용/사용 컷은 공급처 컷을 Image 1 +
  실제 사진을 보조 reference로 고정한다.

### 6.2 파이프라인 사전 검증

전체 배치 전에 **1장짜리 job**으로 인증과 후처리를 먼저 확인한다
(`raw_size` → `final_size`, `matches_expected`).

### 6.3 본 배치 — 동시 실행

`size_mode` / `target_size`는 job 전역이라 비율이 다른 컷을 한 job에 담을 수 없다.
이때 **8×N 순차 배치로 쪼개지 않는다.** 비율별 job을 **동시에 기동**해 provider
동시 요청 총합을 규정 수에 맞춘다.

모든 프롬프트에 품질 게이트 + 제품 불변 조건 블록 + 문자·워터마크 금지를 붙인다.

### 6.4 실패 진단과 재시도

두 종류를 구분한다.

| 유형 | 증상 | 처리 |
| --- | --- | --- |
| 스트림 실패 | 이미지 결과 없이 job 중단, manifest 미생성 | 실패 member만 재시도. 반복 실패하면 **프롬프트 문구·구도를 바꿔** 재시도 |
| 프롬프트 오염 | 지시와 다른 결과 | 원인을 찾는다. 공통 블록이 예외 컷에도 주입된 경우가 대표적 — 해당 컷만 블록을 빼고 반대 조건을 명시 |

**육안 검수는 성공/실패 코드와 별개로 전량 수행한다.** 코드가 성공이어도
지시 위반 컷이 나온다. 통과한 형제 컷은 재생성하지 않는다.

### 6.5 정렬 pair 파생

비포/애프터·단계 컷을 같은 배치에서 따로 생성하면 카메라가 어긋난다.
**base 컷 하나를 먼저 만들고 그것을 Image 1로 둔 `invariant` 편집으로 파생**한다.
프롬프트에 "카메라·프레이밍·크롭·피사체 위치·배율·배경·조명 동일, 아래 항목만 변경"을
고정한다.

### 6.6 승인 자산 확정

의미 있는 이름으로 `generation/approved/`에 복사하고 `approved-manifest.json`에
원본 경로·바이트·SHA-256을 기록한다. 그다음 coverage를 **수치로 확인**한다.

- 이미지 역할 종수 ≥ 요구치
- 장면 종수 ≥ 요구치
- 단독 제품 컷 비율 ≤ 상한
- Hero 후보 복수, 핵심 구조 후보 복수

## 7. 정밀 좌표 — locator guide

치수선·콜아웃·개방 영역은 눈대중으로 놓지 않는다.

1. 승인된 clean source를 Image 1로 둔 `invariant` 편집에서 **마커 점만** 추가한다.
   텍스트·선·화살표·링·글로우는 전부 금지한다.
2. guide마다 기대 마커 수와 각 점의 의미를 먼저 표로 정한다.
3. `scripts/motion/extract-locator-guides.mjs`로 기계 추출한다.
4. **`detected_marker_count == expected_marker_count`**, source/guide 픽셀 크기 동일,
   자산 SHA-256을 확인한다.
5. **역할 라벨이 검출 순서로 붙어 실제 기하와 어긋날 수 있다.** 좌표를 육안 대조해
   축·역할을 직접 재배정한다.
6. 필요하면 점들로 도형을 역산해(예: 회전 타원) SVG에 그대로 넣는다.
7. **가이드 이미지는 pending에만 둔다.** 렌더 입력·poster·HTML·`output/media`
   어디에도 넣지 않는다.

## 8. G3 모션

### 8.1 스캐폴드

`init` 예제 이름이 registry에 없으면 실제 존재하는 예제로 바꾼다. 스캐폴드 하나를
기준으로 **생성 스크립트를 만들어 전 모션 프로젝트를 결정론적으로 생성**한다
(index.html / meta.json / hyperframes.json / package.json / assets 복사).

### 8.2 다양성 표 먼저

모션별로 목적·카메라·핵심 변화·전환·강조 그래픽·pattern을 표로 확정한다.
**인접 모션은 4축 중 최소 3축이 달라야 한다.** pattern은 서로 겹치지 않게 둔다.

### 8.3 결정론 제약 대응

허용 애니메이션 속성 목록에 없는 속성은 쓰지 않는다. 우회 패턴을 설계한다.
예: 마스크 와이프는 `clip-path` 대신 **counter-translate**로 만든다.

```html
<div id="maskWrap">          <!-- overflow:hidden, x 이동 -->
  <div id="maskInner">…</div><!-- 같은 크기 반대 방향 x 이동 -->
</div>
```

`x`만 선형으로 상쇄되어 이미지는 픽셀 고정, 경계선만 움직인다.
`repeat: -1`·`Date.now()`·`Math.random()`을 쓰지 않고 타임라인은 전부
`paused: true`로 전역에 등록한다.

루프는 두 방식 중 하나로 닫는다.

- 상태형: 마지막에 시작 상태로 복귀 → 마지막 프레임 = 첫 프레임
- 오버레이형: 끝에서 오버레이를 전부 페이드아웃 → 첫·끝 프레임 동일

### 8.4 검사와 수정 반복

`check`를 돌리고 나오는 문제를 유형별로 처리한다.

| 유형 | 처리 |
| --- | --- |
| `studio_missing_editable_id` | 씬 루트에 id 부여 |
| `font_family_without_font_face` | 로컬 폰트를 `@font-face`로 선언하고 스냅샷으로 한글 렌더 확인 |
| contrast err | **팔레트를 기준에 맞게 전면 조정**한다. 배경 밝기에 따라 흔들리는 라벨은 솔리드 pill로 바꾼다 |
| `duplicate_media_discovery_risk` | 같은 src·start·duration 중복 → 사본 파일을 만들어 해소 |
| `text_occluded` | 마스크 아래 라벨을 마스크 **바깥**으로 빼고 전환에 맞춰 크로스페이드 |
| layout warn (화면 밖 요소) | 슬라이드 트랙·스윕 마스크처럼 구조상 불가피하면 렌더 결과로 무해함을 확인하고 남긴다 |

**check 통과가 끝이 아니다.** 렌더 프레임을 실제로 보고 의미가 성립하는지 확인한다.
검사 통과했지만 비교가 성립하지 않는 구도가 나올 수 있고, 그때는 설계를 다시 고친다.

### 8.5 렌더와 파생

정본은 **결정론적 무음 MP4** 하나다. HyperFrames 직접 GIF 렌더를 기본 경로로 쓰지
않는다. MP4 하나에서 FFmpeg로 3종을 파생한다.

| 파생본 | 용도 |
| --- | --- |
| animated WebP | 공개 HTML 전달본 |
| GIF | Wing 등 GIF 필수 도구용 |
| poster | 첫 프레임 |

용량 차이가 크면 공개 HTML은 가벼운 쪽을 참조하고 나머지는 파생본으로 보관한다
(동일 모션·동일 프레임임을 기록).

### 8.6 모션 QA

각 MP4에서 first/mid/last 프레임을 뽑아 **전부 육안 검수**한다.

- 첫 프레임에 제품/문제 + 한 줄 메시지 + 시각 근거가 함께 있는가
- 콜아웃이 실제 좌표에 붙는가
- 제품 색·형태·부품이 프레임 간 불변인가
- 마지막→첫 프레임 연결이 튀지 않는가

파일 단위로 애니메이션 실효성도 확인한다(프레임 청크 수가 최소치 이상).

## 9. G4 HTML 조립

1. 승인 정지 이미지를 전달 폭 WebP로 변환한다.
2. 정책 순서 그대로 섹션을 조립한다.
3. 반응형은 폭 `min(100%, 780px)` + 전 타이포 `clamp()`. **하한/상한을 직접 계산해**
   좁은 폭과 넓은 폭 양쪽에서 제목 최소 크기 요구를 넘기게 한다.
4. 제목 줄바꿈은 브라우저 자동 줄바꿈에 맡기지 않고 의미 단위로 직접 끊는다.
   본문은 `word-break: keep-all`.
5. 공개 출력에 `data-*` 0건이 요구되므로 poster 경로를 DOM 속성에 저장하지 않는다.
   **JS 자료구조 + 파일명 규칙**으로 처리한다.
   - 초기 `src`는 실제 animated 파일(공개 DOM animation 참조 수 보장)
   - `IntersectionObserver`로 화면 밖 → poster, 재진입 → animation 재할당
   - `prefers-reduced-motion: reduce` → 전부 poster 고정

### 9.1 브라우저 실측 검수

추정하지 않고 harness로 잰다.

| 검사 | 기준 |
| --- | --- |
| overflow | 여러 폭에서 `scrollWidth − clientWidth == 0`, 넘친 요소 0 |
| 타일 캡처 | 좁은 폭·넓은 폭 전 구간을 잘라 육안 검수 |
| 주 시각 점유율 | 섹션 면적 대비 최대 이미지 면적 ≥ 기준 |
| 타이포 실측 | 각 폭에서 H1/H2 실제 px |
| 모션 동작 | 스크롤 위치별 `src` 목록 변화 + 연속 캡처 2장이 서로 다른지 |

**여기서 나온 발견은 표로 남기고 각각 무엇을 고쳤는지 함께 적는다.** 점유율이
기준에 못 미치면 여백을 줄이고 모션을 full-bleed로 바꾸는 식으로 구조를 고친다.

## 10. G5 게시 QA

### 10.1 공개 금지 스캔

`data-*` / 내부 ID / 해시 / 프롬프트·모델·agent / 로컬 경로 / Studio 링크 /
가짜 후기 UI / 가짜 구매 버튼 / 제작자 언어 — 전부 0건.

**정규식 1차 스캔의 오탐을 그대로 믿지 않는다.** 수치 표현이 잡히면 `<script>`·
`<style>`을 제거한 **고객 노출 텍스트만** 다시 스캔해 판정한다.

### 10.2 animation closure

```
공개 DOM animation 참조 수 == manifest animation 항목 수 == 실제 파일 수
각 파일의 프레임 수 ≥ 최소치
poster-only 전달 0건
```

### 10.3 접근성·무결성

모든 `<img>`가 고객용 alt 보유, 빈 alt 0.
로컬 미디어 참조 수 == manifest 수 == 실제 파일 수, 누락 0.

### 10.4 정리와 매니페스트

HTML이 참조하지 않는 이미지를 `output/media`에서 제거한다(원본은
`generation/approved/`에 보존). `export-manifest.json`에 파일별 바이트·SHA-256,
animation 프레임 수와 파생본 경로를 기록하고 `project.json`의 phase와 QA
report 경로를 갱신한다.

## 11. 작업 로그 작성 규칙

run마다 `.detail-page/planning/BUILD-LOG.md`를 **사후 기록**으로 남긴다.
계획서가 아니다.

- 실제로 실행한 명령, 실제로 받은 출력, 실패 코드, 재시도 결과, 그때의 판단 근거를
  순서대로 적는다.
- 실패를 지우고 성공만 적지 않는다. 재시도로 해결된 것도 실패 → 원인 → 조치로 남긴다.
- 검사 수치는 값 그대로 적는다(before/after 표가 있으면 함께).
- 마지막 두 절은 반드시 넣는다.

| 절 | 내용 |
| --- | --- |
| 하지 않은 것과 그 이유 | 근거 부족·권리 제한·환경 미충족으로 **의도적으로 빼놓은 것**과 판단 근거 |
| 남은 리스크 | partial 번들, 대체 판단, 용량·보관 등 다음 사람이 알아야 할 것 |
